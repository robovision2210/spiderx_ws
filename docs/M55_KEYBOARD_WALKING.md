## 1. Scope, gates and non-claims

**In scope (Cloud):** the gait generator, the locomotion state machine, the command lease, the
gated transport, the node, the keyboard teleop, the launch file, the tests and this document.

**Not done and not claimed:**
- no Gazebo or headless simulation was started; no external ROS graph was contacted;
- no goal was sent to any controller; nothing moved;
- no screenshot, video or runtime metric exists for M5.5;
- the static margin is a **quasi-static approximation** (CAD masses, point feet at the derived
  tips, flat ground, no slip, no dynamics); it is not a proof of balance;
- fault cancellation holds the joints; it does not guarantee a physically safe hold;
- the simulator ground truth used by the development monitor is **not** odometry (M7);

- the node always uses `ShadowTransport`, which verifies and records each goal and sends nothing.

Tests exercise the enabled logic only against the in-memory `FakeLocomotionTransport`, with the
gate set `True` inside the test (`monkeypatch`).

**Preserved:** the M6.0-D one-goal behaviour and identity (`44f0a7ad52e5c330` /

## 2. Free-base gait feasibility: why a crawl, not a trot

Generated by `ros2 run spiderx_controller m55_gait_feasibility` (config SHA-256
`c196513509b1425551066bebfbe52c07eb45c5eea10050af7d91dcf168e867fd`, exit 0).

| Fact (CAD mass model, neutral stance, base_link) | Value |
|---|---|
| Total mass / one leg | 7.458 kg / 1.234 kg (the legs carry 66 %) |
| COM | (51.0, −57.6, 71.7) mm |
| Four-foot static margin | 84.5 mm |
| Three-foot margin with one foot lifted, **no body shift** | FL +3.8, FR +4.0, RL **−4.0**, RR **−3.8** mm |
| Trot: two-foot (diagonal) support | zero area: **no static margin exists**; COM 4.0 / 3.8 mm from the diagonals |

- **Without a body shift, lifting a rear leg tips the robot** (negative margin), and lifting a
  front leg leaves 4 mm. M4.5 found the same: its wave and tripod_crawl gaits fail static
  stability.
- **A trot is not shown to be stable here.** With two feet down there is no support polygon, so
  stability is dynamic. Nothing in this repository has balance feedback, an IMU, real actuator
  data or a measured contact model. Slow playback is not a proof of balance either. A trot is
  therefore **not** claimed as the safest free-base gait. The approved M6.1 trot stays a
  **fixed-base** test case, unchanged and separately tested.
- **A crawl with body shift is stable by construction under its assumptions.** Before each swing,
  the body shifts so that the COM of the coming three-foot phase lies inside the support triangle
  inset by 20 mm. Every template keeps at least 19.4 mm of margin at every dense sample, against
  the 15 mm requirement. The local phases (§10) exist to check those assumptions: flat ground,
  no slip and the CAD masses.

## 3. Architecture and data flow

```
 keyboard (TTY) ──► m55_teleop_keyboard ──/cmd_vel (Twist, 10 Hz heartbeat)──┐
                         │ Trigger calls                                     │
                         ▼                                                   ▼
            /spiderx/locomotion/{arm,disarm,stop,estop,reset,home}   CommandLease (m55_command)
                         │                                                   │ intent
 /joint_states ──────────┤                                                   │
 /spiderx/sim/world_poses┤ (ground truth, development monitor)               │
 graph queries (1 Hz) ───┤                                                   │
                         ▼                                                   ▼
                 ┌────────────────────── LocomotionSession (m55_locomotion) ─────────────┐
                 │ the ONLY decision maker: states, lease, monitors, continuity, homing  │
                 └──────────────────────────────┬───────────────────────────────────────┘
                                                │ one PhaseGoal at a time (fingerprinted)
                 gate False ────────────────────┼──────────────── gate True (not in this build)
                 ShadowTransport: verify, record│               RclpyPhaseTransport: verify, send
                 report done after the plan;    │               FollowJointTrajectory goals to
                 sends NOTHING                  ▼               /leg_trajectory_controller
                               /spiderx/locomotion/status (std_msgs/String, JSON)
```

**Single owner of actuator commands.** The node has exactly one possible action client, created
only by `RclpyPhaseTransport` (gate `True`). It has one publisher, the status topic. Once per
second the node counts:
- publishers on `/leg_trajectory_controller/joint_trajectory` (must be 0);
- FollowJointTrajectory clients on the controller's action, as subscribers of
  `…/follow_joint_trajectory/_action/status`, minus its own (must be 0);
- `/joint_states` publishers (must be exactly 1).

`arm` is refused, and an armed session faults, on any violation. The M6.0-D and M6.1 CLIs are
never looped or reused for walking: they remain one-goal tools.

**Preemption, horizon, continuity.**
- **No preemption.** The next goal is sent only after the previous phase reports `SUCCEEDED`.
- **Horizon.** One phase: 0.6–4.5 s of motion plus a 0.2 s lead-in (at most 4.7 s).
- **Continuity.** Every phase starts and ends at rest with four feet down. Before each goal:
  - the session waits for a `/joint_states` sample received **after** the previous result (the
    two streams are independent);
  - it requires the measured joints to be within 0.02 rad of the phase start;
  - the goal's 0.2 s lead-in moves from the measured state to that start
    (≤ 0.02 rad / 0.2 s = 0.1 rad/s).

## 4. Frames and equations

**Body frame (base_link, not REP-103):** +x robot right, +y robot front, +z up.

**Commands (REP-103 `/cmd_vel`):** linear.x forward, linear.y left, angular.z counter-clockwise.

```
v_base = R(+90°) · v_rep      (forward (1,0) → base (0, +1);  left (0,1) → base (−1, 0))
yaw rate: identical in both frames (both right-handed about +z)
```

- **Supported:** linear.x only, mapped to base +y.
- **Rejected explicitly** (counted, the intent becomes STOP, and the lease is not renewed):
  - |linear.y| > 1e-6 → `command_unsupported_lateral`;
  - |angular.z| > 1e-6 → `command_unsupported_yaw`;
  - any other component → `command_unsupported_axis`;
  - a non-finite or malformed command → `command_nonfinite`;
  - messages closer than 1/50 s → `command_rate_exceeded`.
- **Speed level:** the fastest validated level not faster than the request. A request below the
  deadband (0.2 mm/s) or below the slowest level is a stop. The robot never goes faster than
  asked.

**Body pose (development monitor).** From `/spiderx/sim/world_poses`:

```
T_world_body = T_world_model · T_model_dummy · T_dummy_base
```

- `T_world_model` is the model entry `spiderx`.
- `T_model_dummy` is the `dummy_link` entry, which is model-relative.
- `T_dummy_base` is the identity (`dummy_joint` has no origin).

Tilt is the angle between the body z axis and the world z axis.

**Static margin** = the signed distance from the horizontal COM (from the exact URDF mass model,
configuration-dependent) to the nearest edge of the support polygon. It is positive inside.

**Timing.**
- **Phase durations.** Each phase gets the shortest duration that is a multiple of 0.1 s, is at
  least its minimum (shift 0.5 s, swing 0.6 s) and gives peak |q̇| = max|dq/du| / T ≤
  0.9 × 0.25 rad/s.
- **Level speed** = stride / (cycle + 9 × 0.2 s lead-in). Action result latency is not included.

## 5. The gait: templates and phase goals

**Cycle (forward, stride L).** `S1 W(LR) S2 W(LF) S3 W(RR) S4 W(RF) S5`:
- each shift S moves the body smoothly (zero end velocity) by L/4 plus a sway;
- each swing W moves one foot L forward along a cycloid with a 12 mm apex;
- S5 removes the sway.

Reverse is the forward cycle in reverse time: the same configurations and supports, so the same
validation holds.

**Validation of each template** (every check named, nothing clamped):
- **IK:** solvable at every 20 ms sample within the URDF limits minus 0.05 rad.
- **Joint speed:** |q̇| ≤ 0.25 rad/s.
- **Static margin:** ≥ 15 mm at every sample.
- **Controller spline:** the cubic Hermite through the dispatched 0.1 s waypoints is within
  0.002 rad of the dense path and keeps the margin.

| Stride | Cycle | Speed incl. lead-in | Min static margin | Max \|q̇\| | Max spline error | Phase durations (s) |
|---|---|---|---|---|---|---|
| 20 mm | 17.0 s | 1.06 mm/s | 19.8 mm | 0.225 rad/s | 0.000007 rad | 1.5 2.2 1.5 2.2 2.6 2.3 1.5 2.2 1.0 |
| 40 mm | 19.3 s | 1.90 mm/s | 19.6 mm | 0.225 rad/s | 0.000007 rad | 1.6 3.0 1.0 3.1 2.9 2.8 1.0 2.9 1.0 |
| 60 mm | 23.8 s | 2.34 mm/s | 19.4 mm | 0.225 rad/s | 0.000030 rad | 1.7 4.4 0.6 4.5 3.0 4.0 0.6 4.0 1.0 |

- The body sway is 8–17 mm per shift.
- The worst margin occurs mid-cycle (7.4 / 8.7 / 11.2 s).
- Building all three templates takes about 70–75 s on the 4-core Cloud VM (pure-Python kinematics).
  The node does it at start-up, before its services appear.

These are walking speeds of 1–2.3 mm/s: slow, by design. They follow from the development
joint-speed bound and the provisional parameters, not from a measured limit.

**Phase goals.** Each of the 9 phases × 3 levels × 2 directions is one `PhaseGoal` (54 in all).
A goal consists of:
- the lead-in to the phase start at t = 0.2 s;
- the phase waypoints, unchanged from the validated template;
- zero velocity at both ends;
- path and goal tolerances of 0.05 rad, and a goal-time tolerance of 1.0 s.

Each goal carries a SHA-256 fingerprint over its exact content (names, times, positions,
velocities). Every transport, including the shadow transport, refuses any goal that is not
intact and in the library.

## 6. The locomotion state machine

| State | Meaning | Leaves on |
|---|---|---|
| DISARMED | nothing in flight; motion commands ignored | `arm` (checks below) → READY; `estop` → FAULTED |
| READY | armed, at rest at a validated phase boundary | moving intent → STARTING; lease expiry → DISARMED; `home` → STARTING; `disarm` → DISARMED |
| STARTING | the first phase from rest is sent, awaiting acceptance | accepted → WALKING; zero intent / `stop` → STOPPING; fault → FAULTED |
| WALKING | phases sent one after another while the intent stays moving | zero intent / `stop` / `disarm` / lease expiry → STOPPING; fault → FAULTED |
| STOPPING | controlled stop: the phase in flight completes, nothing more is sent | result → READY (or DISARMED after `disarm` / lease expiry) |
| FAULTED | a fault or `estop`: the goal in flight was cancelled **once**; hold | `reset` (only when no goal is unresolved) → DISARMED |

**Arm checks**, each refused by name. Arm requires:
- the dispatch gate (dispatch mode only) and the action server (dispatch mode only);
- fresh, finite, complete `/joint_states`, with sim time advancing and no reset in the last 5 s;
- a fresh, clean graph (single owner, no topic publisher, one joint-state publisher);
- a fresh, valid body pose with tilt ≤ 0.26 rad;
- the measured posture within 0.02 rad of a validated phase boundary;
- the current command being a stop.

The matched boundary sets where walking resumes. If a mid-cycle boundary of the level last
executed is within tolerance, it is preferred: the same phase of two strides can be close, down
to 0.023 rad.

**Lease (B4).**
- A valid command renews the lease at its receipt time (monotonic). The teleop sends zero-Twist
  heartbeats at 10 Hz.
- No valid command for 0.5 s (counted from `arm` if none arrived) → controlled stop, then
  DISARMED.
- Reconnecting never re-arms: `arm` must be pressed again.
- No key-release event is needed or used.

**Stop latch.** A `stop` request holds until a zero (non-moving) command is seen. Without it, a
still-held key would restart walking after one phase.

**Direction, speed and home.**
- **Reversal** takes effect at the next phase boundary, playing the same phase back.
- **Speed level changes** take effect at the next cycle boundary only, because mid-cycle
  boundaries differ between strides.
- **`home`** walks the fewest phases to the nearest cycle boundary (the neutral stance). It
  ignores motion keys but obeys `stop`, `estop`, faults and lease expiry.

**Faults (B5).** Each fault cancels the goal in flight once, then holds:

| Group | Faults |
|---|---|
| Operator | `estop` |
| Joint states and sim time | `joint_states_stale`, `joint_states_invalid`, `sim_time_stalled`, `sim_time_reset` |
| Body pose | `body_pose_stale`, `body_pose_invalid`, `body_tilt_exceeded` |
| Graph | `graph_status_stale`, `command_owner_conflict`, `command_topic_publisher_present`, `joint_state_publishers`, `action_server_missing` |
| Motion | `continuity_error`, `tracking_error` (feedback \|error\| > 0.05 rad) |
| Goal | `goal_rejected`, `goal_aborted`, `goal_result_unexpected`, `goal_response_timeout` (2 s), `phase_result_watchdog` (duration + 1 s + 1 s) |
| Transport and gate | `transport_error`, `dispatch_disabled` |

Recovery always needs `reset`, then a fresh `arm`. `reset` is refused while the cancelled goal
has not reported a result; restart the node in that case. There is **no automatic recovery
motion**. After a fault mid-phase the posture matches no boundary and `arm` is refused
(`posture_not_at_phase_boundary`). In simulation, restart the simulation (§11).

**Shutdown.** Stopping the node never cancels. The single phase in flight ends at rest at a
validated boundary, which is a controlled stop by construction. The emergency stop is the
explicit `estop` service (teleop `x` or `Esc`).

## 8. Keyboard teleop

```
ros2 run spiderx_controller m55_teleop_keyboard        # in its own terminal (a TTY)
```

| Key | Action |
|---|---|
| `a` | arm |
| `z` | disarm (after a controlled stop) |
| `w` (hold) | walk forward (robot +y) |
| `s` (hold) | walk in reverse |
| space | controlled stop (held until keys are released) |
| `x` or `Esc` | **emergency stop**: cancel and hold; then `r`, then `a` |
| `r` | reset after a fault (→ DISARMED) |
| `h` | home: walk to the nearest cycle boundary |
| `+` / `=` and `-` | faster / slower speed level (bounded to the validated levels) |
| `j` / `l` | turning: **rejected**, "turning is not supported by the current gait"; nothing is sent |
| `q` (or Ctrl+C, Ctrl+D) | quit: stop, disarm, exit |

- **Hold.** A motion key counts as held for 0.8 s after its last auto-repeat. The teleop
  publishes `/cmd_vel` at 10 Hz: the held motion at the selected level's validated speed,
  otherwise zero.
- **Speeds.** They come from the node's status, so the teleop never invents a speed.
- **Escape sequences.** Arrow and function keys are ignored with a message; only a lone `Esc` is
  the emergency stop.
- **Exiting.** If the terminal closes (EOF, SIGHUP) the teleop sends stop and disarm, and the
  lease covers the rest.

## 11. Troubleshooting

| Symptom | Cause | What to do |
|---|---|---|
| no services for ~70–150 s after launch | the node designs and validates its 3 templates at start-up | wait for `locomotion node up` |
| arm refused `joint_states_missing` / `joint_states_stale` | controllers not active yet, or Gazebo paused | wait for both spawners; press play in Gazebo |
| arm refused `sim_time_stalled` | simulation paused or very slow | unpause; check the real-time factor |
| arm refused `body_pose_missing` / `body_pose_invalid` | ground-truth bridge not running (wrong launch) | use `fortress_m55_walking.launch.py` (it includes the bridge) |
| arm refused `command_owner_conflict` | another FollowJointTrajectory client (an M6 tool, `ros2 action send_goal`, rqt) | close it; there must be one owner |
| arm refused `command_topic_publisher_present` | something publishes on `/leg_trajectory_controller/joint_trajectory` | stop it (for example `test_one_joint.py`) |
| arm refused `joint_state_publishers` | 0 or 2+ `/joint_states` publishers (duplicate broadcaster or `joint_state_publisher_gui`) | keep exactly one |
| arm refused `posture_not_at_phase_boundary` | the robot is not in a validated rest posture (e.g. after an emergency stop mid-phase) | restart the simulation (neutral posture hold), then `a`; there is no automatic recovery motion |
| arm refused `arm_requires_stop_command` | a motion key is held while arming | release it, then `a` |
| walking stutters at the first key press | the terminal's key-repeat delay exceeds the 0.8 s hold window | `xset r rate 400 30`, or raise `teleop.hold_s` (provisional) |
| it stopped by itself and is DISARMED | lease expiry: the teleop stopped sending | check the teleop terminal; press `a` again |
| `+` / `-` show "no locomotion status yet" | the teleop has not received the status | check that the node is up and on the same `ROS_DOMAIN_ID` |
| `reset` refused `goal_in_flight_unresolved` | the cancelled goal never reported a result | restart the node (and the simulation) |

## 12. Beginner's guide

- **What walks?** Nothing yet, on purpose. This build plans and checks every step and shows what
  it *would* send. Nothing is sent until the owner approves a separate change.
- **Why so slow?** Every joint moves slowly (under 0.25 rad/s), and before each leg lifts, the
  body leans away from it so the robot cannot tip. One full step of all four legs takes 17–24 s.
- **What is a phase?** One small motion that starts and ends with the robot standing still on
  four feet: either the body shifting, or one leg stepping. The robot is sent one phase at a
  time, so stopping always means "finish this small motion and stand".
- **What does arming do?** It checks that everything is alive and that the robot is standing in
  a known pose. Only then do the keys do anything. If the keyboard program stops, the robot
  stops and disarms by itself.
- **What is the emergency stop?** `x` or `Esc`. It cancels the current motion immediately and
  holds the joints where they are. To continue: `r` (reset), then `a` (arm). After an emergency
  stop in the middle of a step, restart the simulation first.
- **Why no turning?** The validated gait walks straight forward and backward only. Turning keys
  are refused with a message instead of doing something unexpected.
