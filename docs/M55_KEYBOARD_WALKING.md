## 1. Scope, gates and non-claims

**In scope (Cloud):** the gait generator, the locomotion state machine, the command lease, the
gated transport, the node, the keyboard teleop, the launch file, the tests and this document.

**Not done and not claimed:**
- no Gazebo or headless simulation was started; no external ROS graph was contacted;
- no goal was sent to any controller; nothing moved;
- no screenshot, video or runtime metric exists for M5.5;
- the static margin is a **quasi-static approximation** (CAD masses, point feet at the derived
  tips, flat ground, no slip, no dynamics); it is not a proof of balance;
- fault cancellation holds the joints; it does not guarantee a physically safe hold;
- the simulator ground truth used by the development monitor is **not** odometry (M7);
- the joint-speed bound (0.25 rad/s) is a development bound, **not** an actuator rating.

**The M5.5 gate** is one module-level literal, pinned by `test/m55_gate.py`. No CLI flag,
environment variable, ROS parameter, service, key or arming sequence reads or changes it; tests
check this by source inspection. While it is `False`:
- `RclpyPhaseTransport` (the only code that can create the trajectory action client) refuses to
  exist;
- `LocomotionSession` refuses any transport whose mode is `dispatch`;
- the node always uses `ShadowTransport`, which verifies and records each goal and sends nothing.

Tests exercise the enabled logic only against the in-memory `FakeLocomotionTransport`, with the
gate set `True` inside the test (`monkeypatch`).

**Preserved:** the M6.0-D one-goal behaviour and identity (`44f0a7ad52e5c330` /
`0d6ef417…`), the approved M6.1 fixed-base trot (`241760e7dfd5ef12`, content `94a492c4…`,

## 2. Free-base gait feasibility: why a crawl, not a trot

Generated by `ros2 run spiderx_controller m55_gait_feasibility` (exit 0). The preserved report,
regenerated twice from revision `49cdeff` (config SHA-256 `5b243247…`) with identical
deterministic content, is [`docs/evidence/m55/report.json`](evidence/m55/README.md). The original
run at `2857d50` (config `c1965135…`) gave the same figures; its file was lost to a
`rm -rf … log` clean build.

| Fact (CAD mass model, neutral stance, base_link) | Value |
|---|---|
| Total mass / one leg | 7.458 kg / 1.234 kg (the legs carry 66 %) |
| COM | (51.0, −57.6, 71.7) mm |
| Four-foot static margin | 84.5 mm |
| Three-foot margin with one foot lifted, **no body shift** | FL +3.8, FR +4.0, RL **−4.0**, RR **−3.8** mm |
| Trot: two-foot (diagonal) support | zero area: **no static margin exists**; COM 4.0 / 3.8 mm from the diagonals |

- **Without a body shift, lifting a rear leg tips the robot** (negative margin), and lifting a
  front leg leaves 4 mm. M4.5 found the same: its wave and tripod_crawl gaits fail static
  stability.
- **A trot is not shown to be stable here.** With two feet down there is no support polygon, so
  stability is dynamic. Nothing in this repository has balance feedback, an IMU, real actuator
  data or a measured contact model. Slow playback is not a proof of balance either. A trot is
  therefore **not** claimed as the safest free-base gait. The approved M6.1 trot stays a
  **fixed-base** test case, unchanged and separately tested.
- **What the crawl offers instead: an offline, sampled, quasi-static result.** Before each swing,
  the body shifts so that the COM of the coming three-foot phase lies inside the support triangle
  inset by 20 mm. The offline check finds a minimum static margin of 19.4 mm (requirement 15 mm).
  - **Method.** Margins are sampled every 20 ms on the dense IK path and on the controller
    spline. That is a sampled minimum, not a continuous bound; the report gives the largest
    change between neighbouring samples (§5).
  - **Support.** All four feet during shifts. During a swing, the three other feet for the whole
    swing, lift-off to touch-down.
  - **Feet and contact.** Feet are points at the derived foot tips. Contact is **assumed**: no
    forces, friction, slip or compliance are modelled.
  - **COM.** The whole-robot COM from the URDF inertials (CAD steel-density masses), by forward
    kinematics, projected vertically, with a level body.
  - **Status.** This is not a proof that the robot cannot tip. The local phases (§10) exist to
    test exactly these assumptions.

## 3. Architecture and data flow

```
 keyboard (TTY) ──► m55_teleop_keyboard ──/cmd_vel (Twist, 10 Hz heartbeat)──┐
                         │ Trigger calls                                     │
                         ▼                                                   ▼
            /spiderx/locomotion/{arm,disarm,stop,estop,reset,home}   CommandLease (m55_command)
                         │                                                   │ intent
 /joint_states ──────────┤                                                   │
 /spiderx/sim/world_poses┤ (ground truth, development monitor)               │
 graph queries (1 Hz) ───┤                                                   │
                         ▼                                                   ▼
                 ┌────────────────────── LocomotionSession (m55_locomotion) ─────────────┐
                 │ the ONLY decision maker: states, lease, monitors, continuity, homing  │
                 └──────────────────────────────┬───────────────────────────────────────┘
                                                │ one PhaseGoal at a time (fingerprinted)
                 gate False ────────────────────┼──────────────── gate True (not in this build)
                 ShadowTransport: verify, record│               RclpyPhaseTransport: verify, send
                 report done after the plan;    │               FollowJointTrajectory goals to
                 sends NOTHING                  ▼               /leg_trajectory_controller
                               /spiderx/locomotion/status (std_msgs/String, JSON)
```

**Single owner of actuator commands (within this node).** The node has exactly one possible action
client, created only by `RclpyPhaseTransport` (gate `True`). It has one publisher, the status
topic. ROS 2 itself offers no exclusive ownership: the controller accepts goals and topic commands
from anyone. The node therefore **observes** the graph, once per second and freshly for every
service request (including `arm`), and counts:
- publishers on `/leg_trajectory_controller/joint_trajectory` (must be 0);
- FollowJointTrajectory clients on the controller's action, as subscribers of
  `…/follow_joint_trajectory/_action/status`, minus its own (must be 0);
- `/joint_states` publishers (must be exactly 1).

`arm` is refused, and an armed session faults, on any violation it **sees**.

A snapshot is not a lock:
- DDS discovery delays new participants. In the Cloud isolated-domain tests, a late foreign
  client faulted an armed node after 0.36 s. That is an observation, not a bound.
- A commander that appears and leaves between snapshots is not seen.
- A later competing goal would preempt ours, which then ends not SUCCEEDED and faults.

The M6.0-D and M6.1 CLIs are never looped or reused for walking: they remain one-goal tools.

**Preemption, horizon, continuity.**
- **No preemption.** The next goal is sent only after the previous phase reports `SUCCEEDED`.
- **Horizon.** One phase: 0.6–4.5 s of motion plus a 0.2 s lead-in (at most 4.7 s).
- **Continuity.** Every phase starts and ends at rest with four feet down. Before each goal:
  - the session waits for a `/joint_states` sample **received after** the previous result
    **and measured after it**. Its header stamp (sim time) must be newer than every stamp seen
    before the result, and no earlier than the planned end (the sim stamp when the acceptance
    was handled, plus the goal's duration). A queued old measurement delivered late never
    counts. The wait is bounded by `post_result_wait_s` (2.0 s wall) → `post_result_feedback_timeout`;
  - it requires the measured joints to be within 0.02 rad of the phase start;
  - the goal's 0.2 s lead-in moves from the measured state to that start
    (≤ 0.02 rad / 0.2 s = 0.1 rad/s).

## 4. Frames and equations

**Body frame (base_link, not REP-103):** +x robot right, +y robot front, +z up.

**Commands (REP-103 `/cmd_vel`):** linear.x forward, linear.y left, angular.z counter-clockwise.

```
v_base = R(+90°) · v_rep      (forward (1,0) → base (0, +1);  left (0,1) → base (−1, 0))
yaw rate: identical in both frames (both right-handed about +z)
```

- **Supported:** linear.x only, mapped to base +y.
- **Rejected explicitly** (counted, the intent becomes STOP, and the lease is not renewed):
  - |linear.y| > 1e-6 → `command_unsupported_lateral`;
  - |angular.z| > 1e-6 → `command_unsupported_yaw`;
  - any other component → `command_unsupported_axis`;
  - a non-finite or malformed command → `command_nonfinite`;
  - messages closer than 1/50 s → `command_rate_exceeded`.
- **Speed level:** the fastest validated level not faster than the request. A request below the
  deadband (0.2 mm/s) or below the slowest level is a stop. The robot never goes faster than
  asked.

**Body pose (development monitor).** From `/spiderx/sim/world_poses`:

```
T_world_body = T_world_model · T_model_dummy · T_dummy_base
```

- `T_world_model` is the model entry `spiderx`.
- `T_model_dummy` is the `dummy_link` entry, which is model-relative.
- `T_dummy_base` is the identity (`dummy_joint` has no origin).

Tilt is the angle between the body z axis and the world z axis.

**Static margin** = the signed distance from the horizontal COM (from the exact URDF mass model,
configuration-dependent) to the nearest edge of the support polygon. It is positive inside.

**Timing.**
- **Phase durations.** Each phase gets the shortest duration that is a multiple of 0.1 s, is at
  least its minimum (shift 0.5 s, swing 0.6 s) and gives peak |q̇| = max|dq/du| / T ≤
  0.9 × 0.25 rad/s.
- **Level speed** = stride / (cycle + 9 × 0.2 s lead-in). Action result latency is not included.

## 5. The gait: templates and phase goals

**Cycle (forward, stride L).** `S1 W(LR) S2 W(LF) S3 W(RR) S4 W(RF) S5`:
- each shift S moves the body smoothly (zero end velocity) by L/4 plus a sway;
- each swing W moves one foot L forward along a cycloid with a 12 mm apex;
- S5 removes the sway.

Reverse is the forward cycle in reverse time: the same configurations and supports, so the same
validation holds.

**Validation of each template** (every check named, nothing clamped):
- **IK:** solvable at every 20 ms sample within the URDF limits minus 0.05 rad.
- **Joint speed:** |q̇| ≤ 0.25 rad/s.
- **Static margin:** ≥ 15 mm at every sample.
- **Controller spline:** the cubic Hermite through the dispatched 0.1 s waypoints is within
  0.002 rad of the dense path and keeps the margin.

| Stride | Cycle | Speed incl. lead-in | Min static margin | Max \|q̇\| | Max spline error | Phase durations (s) |
|---|---|---|---|---|---|---|
| 20 mm | 17.0 s | 1.06 mm/s | 19.8 mm | 0.225 rad/s | 0.000007 rad | 1.5 2.2 1.5 2.2 2.6 2.3 1.5 2.2 1.0 |
| 40 mm | 19.3 s | 1.90 mm/s | 19.6 mm | 0.225 rad/s | 0.000007 rad | 1.6 3.0 1.0 3.1 2.9 2.8 1.0 2.9 1.0 |
| 60 mm | 23.8 s | 2.34 mm/s | 19.4 mm | 0.225 rad/s | 0.000030 rad | 1.7 4.4 0.6 4.5 3.0 4.0 0.6 4.0 1.0 |

- The body sway is 8–17 mm per shift.
- The worst margin occurs mid-cycle (7.4 / 8.7 / 11.2 s).
- **How the minimum was obtained:**
  - it is the smallest value over samples every 20 ms of the dense IK path and of the
    controller spline: a **sampled** minimum, not a continuous bound;
  - the largest change between neighbouring samples is 0.47 mm at every level, so half a step
    (0.24 mm) between samples would still leave at least 19.1 mm;
  - support, feet, contacts and COM are as in §2.
- Building all three templates takes about 70–75 s on the 4-core Cloud VM (pure-Python kinematics).
  The node does it at start-up, before its services appear.

These are walking speeds of 1–2.3 mm/s: slow, by design. They follow from the development
joint-speed bound and the provisional parameters, not from a measured limit.

**Phase goals.** Each of the 9 phases × 3 levels × 2 directions is one `PhaseGoal` (54 in all).
A goal consists of:
- the lead-in to the phase start at t = 0.2 s;
- the phase waypoints, unchanged from the validated template;
- zero velocity at both ends;
- path and goal tolerances of 0.05 rad, and a goal-time tolerance of 1.0 s.

Each goal carries a SHA-256 fingerprint over its exact content (names, times, positions,
velocities). Every transport, including the shadow transport, refuses any goal that is not
intact and in the library.

## 6. The locomotion state machine

| State | Meaning | Leaves on |
|---|---|---|
| DISARMED | nothing in flight; motion commands ignored | `arm` (checks below) → READY; `estop` → FAULTED |
| READY | armed, at rest at a validated phase boundary | moving intent → STARTING; lease expiry → DISARMED; `home` → STARTING; `disarm` → DISARMED |
| STARTING | the first phase from rest is sent, awaiting acceptance | accepted → WALKING; zero intent / `stop` → STOPPING; fault → FAULTED |
| WALKING | phases sent one after another while the intent stays moving | zero intent / `stop` / `disarm` / lease expiry → STOPPING; fault → FAULTED |
| STOPPING | controlled stop: the phase in flight completes, nothing more is sent | result → READY (or DISARMED after `disarm` / lease expiry) |
| FAULTED | a fault or `estop`: the goal in flight was cancelled **once**; hold | `reset` (only when no goal is unresolved) → DISARMED |

**Arm checks**, each refused by name. Arm requires:
- the dispatch gate (dispatch mode only) and the action server (dispatch mode only);
- fresh, finite, complete `/joint_states`, with sim time advancing and no reset in the last 5 s;
- a clean graph snapshot no older than one graph period (the node takes a fresh one for the
  request): no other commander visible, one joint-state publisher;
- a fresh, valid body pose with tilt ≤ 0.26 rad;
- the posture policy below;
- the current command being a stop.

**Arm posture policy** (`resolve_arm_posture`, pure and tested branch by branch):

| Measured posture (all joints within 0.02 rad of…) | Rest record of this process | Result |
|---|---|---|
| nothing validated | any | refused `posture_not_at_phase_boundary` |
| the neutral stance and a mid-cycle boundary | any | refused `posture_ambiguous` |
| the neutral stance | any or none | accepted at boundary 0; the first motion command chooses the level |
| a mid-cycle boundary | none: fresh process, or the last goal was interrupted | refused `posture_mid_cycle_unverified` |
| a mid-cycle boundary | the same (level, boundary) | accepted there; that level continues until the cycle boundary |
| a mid-cycle boundary | a different one | refused `posture_not_at_last_rest` |
| a mid-cycle boundary, in shadow mode | any | refused (shadow records describe the plan, not the robot) |

Why the neutral stance is safe to accept even after an interruption:
- the phases adjacent to it, S1 and S5, are four-foot body shifts;
- every waypoint of every other phase is more than 0.04 rad from neutral (tested on the real
  templates).

Why mid-cycle needs the record:
- a posture within tolerance of a boundary could be partway into the adjacent swing, with one
  foot slightly lifted;
- the same phase of two strides can be as close as 0.023 rad, so the level is not identifiable.

How the record is kept:
- **Set** by `arm`, by a phase that reports SUCCEEDED (also after a cancel that came too late),
  and by a rejected goal (the robot never moved).
- **Cleared** when a goal is sent, and left unknown if that goal is cancelled, aborted,
  unanswered or fails to send.
- It lives in memory only: a fresh process has none.

**Lease (B4).**
- A valid command renews the lease at its receipt time (monotonic). The teleop sends zero-Twist
  heartbeats at 10 Hz.
- No valid command for 0.5 s (counted from `arm` if none arrived) → controlled stop, then
  DISARMED.
- Reconnecting never re-arms: `arm` must be pressed again.
- No key-release event is needed or used.

**Stop latch.** A `stop` request holds until a zero (non-moving) command is seen. Without it, a
still-held key would restart walking after one phase.

**Direction, speed and home.**
- **Reversal** takes effect at the next phase boundary, playing the same phase back.
- **Speed level changes** take effect at the next cycle boundary only, because mid-cycle
  boundaries differ between strides.
- **`home`**, on request only:
  - **Prerequisite.** Accepted only in READY; refused elsewhere (`not_ready`). It is never
    started by reset, re-arm, reconnection or fault recovery.
  - **Movement.** It walks the fewest phases to the nearest cycle boundary (the neutral stance):
    at most 4 phases, and at most 12.0 s sim at the 60 mm level. It stays at the current level.
  - **Gating.** Every phase is sent through the same `_dispatch` as walking: gate, continuity,
    fingerprint, one goal at a time.
  - **Behaviour.** It ignores motion keys and obeys `stop`, `estop`, faults and lease expiry
    (heartbeats are still required).

**Faults (B5).** Each fault cancels the goal in flight once, then holds:

| Group | Faults |
|---|---|
| Operator | `estop` |
| Joint states and sim time | `joint_states_stale`, `joint_states_invalid`, `sim_time_stalled`, `sim_time_reset` |
| Body pose | `body_pose_stale`, `body_pose_invalid`, `body_tilt_exceeded` |
| Graph | `graph_status_stale`, `command_owner_conflict`, `command_topic_publisher_present`, `joint_state_publishers`, `action_server_missing` |
| Motion | `continuity_error`, `tracking_error` (feedback \|error\| > 0.05 rad) |
| Goal | `goal_rejected`, `goal_aborted`, `goal_result_unexpected`, `goal_response_timeout` (2 s wall), `phase_result_watchdog` (duration + 1 s + 1 s in **sim** time; wall backstop at that / 0.1), `post_result_feedback_timeout` (2 s wall) |
| Transport and gate | `transport_error`, `dispatch_disabled` |

**What a fault does, as implemented.** It requests cancellation of the goal in flight **once**
and sends nothing afterwards. That the controller then stops and holds the current position is
the joint_trajectory_controller's intended cancel behaviour. It has **no runtime evidence** in
this repository yet; phase 2 (§10) records it. If the cancel is lost or refused, the phase can
run to its end.

Recovery always needs `reset`, then a fresh `arm`, under the posture policy above:
- `reset` is refused while the cancelled goal has not reported a result; restart the node in that
  case.
- There is **no automatic recovery motion**.
- After a fault mid-phase the posture is usually near no boundary, or near one without a valid
  record, so `arm` is refused. In simulation, restart the simulation (§11).

**Shutdown.** Stopping the node never cancels. The single phase in flight is left to the
controller, which is expected to finish it at a validated rest boundary (a controlled stop, not
yet observed in a run). The emergency stop is the explicit `estop` service (teleop `x` or
`Esc`).

| Value | Setting | Origin |
|---|---|---|

| Post-result fresh sample | ≤ 2.0 s **wall** | bounded wait (§3) |

| Sim-time stall | 5.0 s | = M6.1-A |

| Graph check period / stale | 1.0 s / 3.0 s | — |

## 8. Keyboard teleop

```
ros2 run spiderx_controller m55_teleop_keyboard        # in its own terminal (a TTY)
```

| Key | Action |
|---|---|
| `a` | arm |
| `z` | disarm (after a controlled stop) |
| `w` (hold) | walk forward (robot +y) |
| `s` (hold) | walk in reverse |
| space | controlled stop (held until keys are released) |
| `x` or `Esc` | **emergency stop**: cancel and hold; then `r`, then `a` |
| `r` | reset after a fault (→ DISARMED) |
| `h` | home: walk to the nearest cycle boundary |
| `+` / `=` and `-` | faster / slower speed level (bounded to the validated levels) |
| `j` / `l` | turning: **rejected**, "turning is not supported by the current gait"; nothing is sent |
| `q` (or Ctrl+C, Ctrl+D) | quit: stop, disarm, exit |

- **Hold.** A terminal reports characters, never key releases. A motion key counts as held for
  0.8 s after its last character (the first press or an auto-repeat). The teleop publishes
  `/cmd_vel` at 10 Hz: the held motion at the selected level's validated speed, otherwise zero.
  - **Delay assumption.** The auto-repeat delay and rate belong to the operator's environment
    (§16.2). If the delay exceeds 0.8 s, a held key stops between the first press and the first
    repeat. The teleop then prints `key repeat gap … > hold window`.
  - **A tap** starts at least one full phase.
- **Speeds.** They come from the node's status, so the teleop never invents a speed.
- **Escape sequences.** Arrow and function keys are ignored with a message; only a lone `Esc` is
  the emergency stop.
- **Exiting.** If the terminal closes (EOF, SIGHUP) the teleop sends stop and disarm, and the
  lease covers the rest.

## 12. Beginner's guide

- **What walks?** Nothing yet, on purpose. This build plans and checks every step and shows what
  it *would* send. Nothing is sent until the owner approves a separate change.
- **Why so slow?** Every joint moves slowly (under 0.25 rad/s), and before each leg lifts, the
  body first leans away from it. Offline, with ideal contacts, CAD masses and flat ground, that
  keeps the centre of mass at least 19 mm inside the feet that stay down. Whether the simulated
  (and later the real) robot behaves that way is what the local phases test. One full step of all
  four legs takes 17–24 s of simulation time.
- **What is a phase?** One small motion that starts and ends with the robot standing still on
  four feet: either the body shifting, or one leg stepping. The robot is sent one phase at a
  time, so stopping always means "finish this small motion and stand".
- **What does arming do?** It checks that everything is alive and that the robot is standing in
  a known pose. Only then do the keys do anything. If the keyboard program stops, the robot
  stops and disarms by itself.
- **What is the emergency stop?** `x` or `Esc`. It asks the controller once to cancel the current
  motion; the controller is expected to hold the joints where they are (not yet observed in a
  run). To continue: `r` (reset), then `a` (arm). After an emergency
  stop in the middle of a step, restart the simulation first.
- **Why no turning?** The validated gait walks straight forward and backward only. Turning keys
  are refused with a message instead of doing something unexpected.

### 16.1 Stopping timeline

**Clocks.** Detection runs on **wall** time (monotonic):
- teleop hold window H = 0.8 s;
- heartbeat B = 0.1 s;
- lease L = 0.5 s;
- session tick T = 0.05 s;
- graph period G = 1.0 s;
- the monitors.

The controller executes phases in **sim** time. The longest phase goal is 4.7 s sim (60 mm level;
2.8 s and 3.3 s at 20 and 40 mm), including the 0.2 s lead-in. In wall time, sim durations take
1/RTF as long (about 4–5× at the owner's recorded RTF of 0.21–0.25). **No wall-time bound on
remaining motion exists without a real-time-factor assumption.** The only RTF assumption in the
code is the watchdog backstop (RTF ≥ 0.1).

**The hold window and the lease never add up.** They act on different events:
- **H** belongs to the teleop and decides **what** it sends: the held motion until H after the
  last character, then zeros.
- **L** belongs to the node and covers **whether anything arrives**.
- **Key release.** The teleop keeps sending heartbeats, so the lease never expires: the
  detection is H (+ B + T).
- **Teleop loss.** Nothing arrives, so H is irrelevant: the detection is L (+ T) after the last
  command.

| Event | Detection (wall) | Transition | Commands / cancellation | Max remaining commanded motion (sim) | Recovery |
|---|---|---|---|---|---|
| Movement-key release, or loss of key repeat (focus loss, SSH stall, repeat delay > H) | H after the last character, then ≤ B + T: **0.8–0.95 s** (tested) | WALKING/STARTING → STOPPING (READY if at rest) | no new goal after detection; no cancel | the phase in flight (≤ 4.7 s). If a phase boundary fell inside the detection window, one more phase was already sent: ≤ remainder + 4.7 s | READY at the boundary; a new key press walks |
| Space (controlled stop) | the `stop` service, handled on arrival (no tick wait); plus zeros from the teleop | → STOPPING; stop latch set | no new goal; no cancel | the phase in flight (≤ 4.7 s) | READY; the latch clears on the first zero command (a still-held key does not restart walking) |
| Explicit disarm (`z`) | the `disarm` service, on arrival | → STOPPING, then DISARMED (READY → DISARMED at once) | no new goal; no cancel | the phase in flight (≤ 4.7 s) | `a`: neutral, or this process's rest record |
| Teleop quits cleanly (`q`, Ctrl+C/D, EOF, SIGHUP, SIGTERM) | zero + `stop` + `disarm`, best effort within 1 s | as disarm | as disarm | the phase in flight | `a` after restarting the teleop |
| Teleop crash, kill or network partition | L after the last valid command, then ≤ T: **≤ 0.55 s** (tested) | → STOPPING, then DISARMED | no new goal; no cancel | the phase in flight; one more if a boundary fell within L + T (the last command was still "moving") | DISARMED; reconnecting never re-arms |

### 16.2 Terminal key semantics (environment assumptions)

- **Characters, not key events.** A terminal delivers characters. There is no key-up event, so
  the teleop infers "held" from repeated characters.
- **Who generates the repeats:**
  - the operator's windowing system (X11: `xset q` shows "auto repeat delay … repeat rate";
    GNOME: `gsettings get org.gnome.desktop.peripherals.keyboard delay` and `repeat-interval`;
    Wayland: the compositor's keyboard settings);
  - or the Linux console (`kbdrate`);
  - over SSH, the client machine generates them, and network delay adds jitter.
- **Typical values differ.** They depend on the environment (the X server's built-in default
  delay is 660 ms; desktops commonly set 250–600 ms). None is assumed: phase 1 records the
  operator's values (check 1.11).
- **Effects:**
  - if the first repeat comes later than H = 0.8 s, walking stops between the first press and the
    first repeat, and the teleop prints `key repeat gap … > hold window`;
  - with auto-repeat disabled, every press is a tap;
  - a lagging connection that delays characters by more than H stops the robot (zeros are sent
    meanwhile);
  - characters that arrive in a burst after a lag re-extend the hold from their arrival time.
- **Tested** (`test_m55_review.py`):
  - a held key with a 0.5 s delay and 30 Hz repeat is continuous;
  - a 1.0 s delay stutters and warns;
  - release-to-stop is between 0.8 and 0.95 s;
  - a tap sends nothing after the hold window;
  - teleop loss stops within 0.55 s;
  - a reconnecting teleop never re-arms.
